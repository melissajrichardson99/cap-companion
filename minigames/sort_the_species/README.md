# Sort the Species

Godot 4.x project (GDScript only). Open `project.godot` in the Godot editor to test and export.

## Gameplay
- 3-lane "Auto-Scroll" sorting game, deliberately extending Obstacle Dodge's continuous-position collision approach: items are plain data (`items: Array` of `{lane, x, y, species}` dicts) drawn every frame via `_draw()` (no per-item scene nodes), falling at a constant `FALL_SPEED` in continuous float coordinates, evaluated with the same threshold-crossing style as Obstacle Dodge's `PLAY_BOTTOM` check and the same `LANE_COUNT`/`LANE_WIDTH`/`_lane_x` lane math. The difference from Obstacle Dodge: instead of the player dodging obstacles that move in fixed lanes, here the *items themselves* are player-draggable in `x` (not lane-locked at spawn) while `y` always advances every physics frame regardless of drag state — dragging never pauses or alters the fall.
- 3 bins sit at the bottom, one per lane, each assigned a species (Capybara/Alpaca/Chicken) shuffled once at `_start_game()`. Each bin renders a procedurally-drawn shape+color icon (`_draw_species_icon`) plus a text `Label` naming it — no emoji, per this repo's confirmed Web-export "tofu" missing-glyph gotcha (see project memory / Card Flip Pairs).
- Items spawn one at a time from the top at a random `x` (not lane-aligned) and a random species. Tap/click-and-drag near a falling item to grab it (nearest item within `GRAB_RADIUS`); while held, its `x` follows the pointer (clamped to the play width) but `y` keeps falling on its own schedule. Release just drops the hold reference — the item keeps falling at whatever `x` it was last dragged to. Un-dragged items fall straight down and land wherever their spawn `x` happens to be, which is correct only by chance (~1/3 of the time) — this is what gives dragging real weight.
- Evaluation: when an item's `y` crosses `PLAY_BOTTOM`, its lane is computed from its current `x` (`_lane_from_x`, the inverse of `_lane_x`) and compared against that lane's assigned species — match increments `correct_count`, mismatch increments `missed_count`. The item is pruned from `items` either way, and the hold reference is released if that item was the one currently held.
- Win: `correct_count >= TARGET_CORRECT` (8). Lose: `missed_count >= MAX_MISSES` (4) — ends the round immediately, same as Obstacle Dodge's immediate-loss-on-collision, not a timer wait.
- Round opens with the same "Ready? 3 2 1 Go!" countdown as every other minigame here, guarded by the `round_token` pattern.
- "Play Again" on the game-over screen calls `_start_game()` directly (no scene reload) and reshuffles bin assignments for the new round.

## Constants landed on (and why)
- `FALL_SPEED = 140.0` px/s — travel time from spawn to `PLAY_BOTTOM` is ~3.1s, enough reaction time to notice a falling item, decide, and drag it across up to two lanes before it lands.
- `SPAWN_INTERVAL = 2.6`s, wired via `spawn_timer.wait_time = SPAWN_INTERVAL` in `_ready()` (see gotcha below) — tuned empirically with a Playwright bot (see Verification) so both a near-perfect player (win, ~27s total) and a totally passive non-dragging player (lose, ~29s total) land close to the repo's ~30s/round target, rather than just eyeballing it. The original suggestion of `1.5` produced a ~18s win / ~15s lose round — well under target.
- `TARGET_CORRECT = 8`, `MAX_MISSES = 4` — used as suggested, unchanged.
- `GRAB_RADIUS = 42.0` — generous touch-forgiving grab distance relative to `ITEM_RADIUS = 18.0`.

## What to verify (per the tech spec's known pitfalls)
- Lane-index math at evaluation time must use the item's *current* `x` (post-drag), not its spawn lane — confirmed via a deterministic debug build (forced spawns, fixed bin order) that an item dragged from lane 0 into lane 2 correctly resolves against lane 2's assigned species.
- An un-dragged item landing in a mismatched lane must count as a miss, not be silently ignored — confirmed with the same deterministic build.
- Held-item bookkeeping across array pruning: removing item `i` from `items` shifts every later index down by one, so `held_index` must be adjusted (`_remove_item`) whenever it points past the removed index, or a drag in progress could silently start tracking the wrong dictionary. Exercised implicitly by every drag test since multiple items are usually in flight at once.
- Round pacing under both a highly-attentive and a passive player (see below), not just the nominal constants.

## Verification performed (Playwright against real exported Web builds)
All runs used a local static file server with correct `.wasm`/`.pck` MIME types and COOP/COEP headers, per this repo's established verification workflow.

1. **Deterministic lane-arithmetic + drag test** (throwaway debug copy: fixed bin order `[Capybara, Alpaca, Chicken]`, two forced items spawned synchronously at Go! instead of random spawns, plus a temporary `window.__sortState` JS telemetry broadcast for exact assertions) — **PASS**. An untouched item spawned in the Chicken lane as a Capybara correctly incremented `missed_count` to 1; a second item spawned in the Capybara lane as a Chicken, dragged live (tracking its true falling `y` via telemetry) into the Chicken lane, correctly incremented `correct_count` to 1.
2. **Win path**: a telemetry-only debug build (identical RNG/logic to shipped, only added observability) driven by a Playwright bot with full state visibility that continuously re-targets every mismatched item toward its correct bin — reached `correct_count = 8`, `missed_count = 0`, win screen ("Great Sorting!") displayed, `minigame-complete` postMessage fired. **PASS**.
3. **Lose path**: same telemetry build, passive mode (bot never touches the mouse) — missed count reached 4 (correct count trailing behind, consistent with ~1/3 correct-by-chance for untouched items), lose screen ("Too Many Missed") displayed, `minigame-complete` fired. **PASS**.
4. **Play Again**: after a lose, clicking "Play Again" resets `correct_count`/`missed_count` to 0 and reshuffles `bin_species` for a genuinely new round (confirmed both by telemetry once round 2 reached Go!, and by round 2 playing out a full independent passive loss). **PASS**.
5. **Exit paths**: both the top-bar "X" (mid-round) and the GameOverLayer "Exit" button (post-round) fire `minigame-complete`, confirmed against the real shipped build for the top-bar case. **PASS**.
6. **Pacing**: measured directly (not eyeballed) via the bots above — near-perfect play wins at ~26.7s total (incl. countdown), passive play loses at ~29.4s total. Both land close to the ~30s target.
7. Screenshots confirm bins render distinct icons + labels correctly (tan-and-eared Capybara, white pointy-eared Alpaca, orange comb-topped Chicken diamond) with no emoji/tofu-box rendering issue, and both the win and lose game-over screens render the expected result/summary text and buttons.

All debug/telemetry edits were made only in scratch copies of the project outside `minigames/sort_the_species/`; the shipped `scripts/Main.gd` and `scenes/Main.tscn` were diffed/re-read after testing to confirm no debug code survived. The two real, non-debug fixes discovered *during* this verification and carried into the shipped files are documented below.

## Gotchas discovered this session
- **`TopBar`/`Bins` `Control` nodes silently swallow drag input.** Both cover a rectangular region of the play field (`TopBar`: y 0-60, overlapping where items spawn at `y = PLAY_TOP - ITEM_RADIUS = 42`; `Bins`: y 500-600, near the landing threshold). Godot `Control` nodes default to `mouse_filter = STOP`, which fully absorbs mouse/touch press events landing anywhere in their rect — even where nothing is actually drawn (a `Control` with no background is still hit-tested) — before `_unhandled_input` ever sees them. This silently broke grabbing an item in the first ~instant after it spawns. Fixed by setting `mouse_filter = 2` (`IGNORE`) on both `TopBar` and `Bins` in `Main.tscn`; their child `Button`s (ExitButton, etc.) are unaffected and still consume clicks on themselves specifically, since a child's own `mouse_filter` is independent of its parent's. Caught only by an automated drag test that failed with a suspiciously "silent" miss — worth checking for in any other minigame here where draggable/tappable game-world content spawns underneath a full-width/height UI `Control` bar.
- **A declared constant that isn't wired to anything is a real gotcha.** `SPAWN_INTERVAL` was declared but never assigned to `spawn_timer.wait_time` — the actual spawn cadence was silently coming from the `.tscn`'s hardcoded `wait_time` instead. Fixed by adding `spawn_timer.wait_time = SPAWN_INTERVAL` in `_ready()`, making the GDScript constant the actual source of truth (a small improvement over Obstacle Dodge's convention, which has no equivalent constant at all and just hardcodes the Timer's `wait_time` in the scene).
- **A full-state JS telemetry broadcast (`window.__sortState`) is a much stronger debug technique than pixel/vision reading for drag-and-collision games.** Broadcasting the entire `items`/`bin_species`/`correct`/`missed` state as JSON via `JavaScriptBridge.eval` every physics frame let a Playwright bot make exact, informed drag decisions (grab the right item, drag toward the actually-correct lane) and let assertions check exact counts instead of screenshots — while still exercising the real compiled/exported wasm build end-to-end, not a logic port. Reverted before shipping in both scratch copies used for it; not present in the shipped `Main.gd`.
